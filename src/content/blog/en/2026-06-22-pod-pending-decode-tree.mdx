A Pod sits in `Pending`. It's one of my favorite questions to ask in mock interviews on our DevOps podcast, because it sounds trivial and almost nobody answers it cleanly. Senior candidates included.

<img src="/blog-assets/2026-06-22-pod-pending-decode-tree/cover.webp" alt="Cover slide: Your Pod is stuck in Pending. kubectl get pod shows api-7d9f at READY 0/1." width="1080" height="1350" />

In the interview, I describe the symptom. The candidate types `kubectl logs` in their head, and then they stall, because the logs return nothing. A surprising number of people have no second move.

The second move is to read the Pod's events. The decode tree fits in four lines:

1. A Pending Pod has no container, so logs are empty. Read the events instead.
2. Run `kubectl describe pod` and find the scheduler's `FailedScheduling` line at the bottom.
3. Match the reasons in that line to the four checks: resources, taints, affinity, unbound PVC.
4. No events at all? Check `spec.schedulerName` for a scheduler that isn't running.

## Why logs are empty

Here, `Pending` means the API server has accepted the Pod, but the scheduler hasn't placed it on a node yet. No node means no kubelet picked it up. No kubelet means no container runtime started anything. No container means there are no logs to read.

So `kubectl logs` is the wrong tool. The command doesn't fail, but it has nothing to show: the Pod object exists in etcd, and nothing has run. The cause is in the Events.

## Step 1: read the events with describe

When a Pod stays in `Pending`, run `kubectl describe pod api-7d9f` and scroll to the Events at the bottom. The scheduler writes its reasoning there, and it is specific:

<HtmlEmbed src="/embeds/pod-pending/02-describe-events.html" title="kubectl describe pod output: a FailedScheduling event with a node count for each reason" minHeight={760} />

That single `FailedScheduling` line is the whole answer, broken down by reason, with a node count for each. Twelve nodes, and none of them can take the Pod, for three different reasons. No guessing. The scheduler already did the diagnosis for you. You just have to read it.

The candidates who get this right say "describe" before I finish the question. The ones who don't reach for `logs`, `get pods -o yaml`, or start SSHing into nodes. The difference is whether they have watched a Pod fail to schedule in production.

## Step 2: match the reasons to the four checks

To read those reasons, you need a model of the scheduler. It runs every Pending Pod through a sequence of filters. A node that fails any one of them is out. If no node is left, the Pod stays `Pending`. The order in the diagram is for reading, not the scheduler's own filter order.

<HtmlEmbed src="/embeds/pod-pending/01-scheduling-flow.html" title="Scheduling flow: three gates, then Assigned or Pending" minHeight={840} />

Four checks cover almost everything. Each one leaves a typical phrase in the event.

### Insufficient resources

Look for `Insufficient cpu` or `Insufficient memory`. No node has enough free `cpu` or `memory` for the Pod's `requests`. This is about requests, not actual usage. A node running at 10% CPU can still reject a Pod when the Pods already on it have requested all of its CPU. To fix it, lower the requests, scale the nodes, or add capacity.

<HtmlEmbed src="/embeds/pod-pending/04-requests-not-usage.html" title="Requests, not usage: a node at 10% CPU usage rejects a Pod" minHeight={580} />

### Untolerated taint

Look for `untolerated taint`. The nodes carry a taint the Pod doesn't tolerate. This is common on control-plane nodes, GPU pools, and Spot capacity, where taints exist precisely to keep general workloads off. To fix it, add a matching `toleration` to the Pod spec.

### Affinity not satisfied

Look for `didn't match Pod's node affinity/selector`. No node matches the Pod's `nodeAffinity` or topology spread constraints. Often this is a typo in a node label, or a rule that was written for a cluster that has since changed. To fix it, relax the rule, or label more nodes to match.

### Unbound PVC

Look for `unbound immediate PersistentVolumeClaims` or `didn't find available persistent volumes to bind`. The Pod references a PersistentVolumeClaim that has no matching PersistentVolume or StorageClass. The Pod can't schedule until the volume binds, and if the storage class can't provision, it waits forever. This one catches people because the Pod spec looks fine. The problem is one level down, in the volume.

Match each reason to one of these four and you will resolve the overwhelming majority of Pending Pods. But there's one case that breaks the whole approach: nothing to match.

## The senior follow-up: no events at all

This is where I separate the people who have operated clusters from the people who have only read about them.

What if you run `describe` and there are no scheduling events at all? No `FailedScheduling`, no warnings, nothing. The Pod just sits there in silence.

Then check `spec.schedulerName`:

```bash
kubectl get pod api-7d9f -o jsonpath='{.spec.schedulerName}'
```

It prints `default-scheduler` unless the Pod names another scheduler. Here it prints `gpu-scheduler`.

<HtmlEmbed src="/embeds/pod-pending/03-schedulername-trap.html" title="The schedulerName trap: Pending with no events" minHeight={700} />

By default, Pods are handled by the `default-scheduler`. But you can assign a Pod to a custom scheduler by name. If that name points to a scheduler that isn't running in the cluster, nothing happens. The default scheduler ignores the Pod because it's not its responsibility. The named scheduler doesn't exist to claim it. So the Pod waits, and because no scheduler ever looked at it, there are no `FailedScheduling` events to read.

To fix it, install that scheduler or remove `schedulerName` from the manifest.

I've seen this happen. A team copied a manifest from a GPU-scheduling setup that used a custom scheduler, pasted it into a normal namespace, and couldn't see why the Pod never moved. The events were empty because the scheduler they named was never installed.

That's the answer that gets you hired. Not the four checks, which a good junior can recite. The recognition that an empty event list is itself a clue, and knowing exactly where to look next.

Here is the full picture from my book. The scheduling cycle runs top to bottom through the gates, and the scheduler selection branch on top is the `schedulerName` check that produces the silent case. The four lines at the top take about thirty seconds to say out loud. They show that you understand what the scheduler does, rather than memorizing kubectl commands. That's the whole point of the question.

Watch the events, not the logs. When the events are empty, find out which scheduler was supposed to write them.
